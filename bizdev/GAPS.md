# GAPS: the engineering backlog, ranked by commercial value

Ranked 2026-11-06 from the 2026-11-05 scale report, CLAIMS.md and the buyer map. Each item names the buyers it
unlocks (BUYERS.md segments) and the claims it changes (CLAIMS.md ids). Re-rank weekly and after any benchmark run
that changes a grade. Items 0 and 1 are decisions and contracts, not kernels; they outrank every optimisation
because no buyer can take the code while they stand.

| 0 | **License decision** (IP.md). The current license is non-OSI and forbids commercial use without a paid license: every open-source engine, every standard library and runtime, and most corporate legal departments cannot take the code at all. Not an engineering item, but it gates ranks 1-12. | any integration | all except "hire" | none directly; makes every green row usable | decision |
| 1 | **Reentrancy: `logos_sort_f64` callable from many threads at once.** Today the context pool, bundle table, worker pool and diagnostics are process globals and concurrent calls gave wrong output. Engines sort thousands of blocks concurrently, one per pipeline thread, with `nthreads = 1` each. The shape of the fix: an explicit context object (`logos_ctx_t *`) or thread-local pools, with the one-call-at-a-time entry kept as a wrapper. Then measure 14 concurrent one-thread sorts of 1M against 14 concurrent x86-simd-sort calls. | the real deployment pattern of every analytics engine | DuckDB, ClickHouse, Polars, DataFusion, Velox, Spark, proprietary engines | R7 -> green; makes G1-G8 usable | medium |
| 2 | **Routing gate that allocates only on a predicted win.** Take the partition's scratch (and the one-thread 16 B/el) only when the sample predicts the structured route wins by about 1.3x or more; otherwise run the in-house AVX2 quicksort in place. Group C (uniform, heavy_tail, bimodal, int_wide, sine_slope) would read "level at 0 B/el" instead of "level at 16". The resident figure is already near 0 on that path (`rssprobe`), so half of this is accounting: do not malloc what the path never touches, and report resident and traced peak side by side in the scale report. | memory-budgeted engines (buffer managers count allocations, not pages touched) | DuckDB, Velox, Spark, proprietary | A8, A9, R1 memory half; new claim "level with x86-simd-sort at 0 B/el on random data" | medium |
| 3 | **Memory-budget API: `logos_sort_f64_budget(a, n, nthreads, scratch_bytes)`.** Three modes by budget: full (16 B/el), a middle mode (half a scratch: the `half_place` machinery exists at one thread, 4.1-4.4 B/el; the in-place partition at 14 threads is 1.4-2.2 B/el for 1.25-1.38x time), and the strict in-place path. ## Notes on ordering

- Items 0-1 before anything else: a faster engine that cannot be licensed or called concurrently changes no buyer's
  answer. Item 1 also unblocks a fair measurement of the deployment pattern (many one-thread sorts in parallel),
  which no bench here runs.
- Items 2-3 convert the memory story. Today Group C reads "level or behind while allocating 16 B/el"; after 2 it
  reads "level at 0"; after 3 the buyer chooses the trade.
- Items 4-5 are what makes the green rows describe a buyer's data. A sort of bare doubles is a benchmark, not an
  operator.
- Item 7 is cheap and should run alongside everything: the `urls` memory defect and the missing PASSIVE wait policy
  are the two that a reader of the report will find first.
- Re-rank triggers: a license decision (moves 0 out, promotes 1-3), a second machine (may demote or promote rows
  in CLAIMS), a buyer conversation that names a block size or a type.
