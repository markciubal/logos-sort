# logos-sort (Rust)

> **Parity status (read first; 2026-11-11).** `sort_f64` is **the C flagship's algorithm**: `src/port/` is a
> transliteration of `engines/c/logos_psort.c` (the f64 sort, default build; about 10,000 lines), with the same routes
> in the same order, the same gates and the same constants. It is checked against the C engine by WHICH ROUTE RAN, in
> one binary (`parity/routes.sh`): on 72 shapes from 2 to 8.4M elements at 1 to 14 threads (4,320 cells) every output
> is correct and every route witness the C engine keeps (which route fired, kinks repaired, strays lifted, lattice
> vectors counted...) reads the same in Rust, exactly at one thread and within run-to-run range with threads. Its SPEED
> is level with the C's on 26 of the scoreboard's 34 cells at 8.4M and 7-24% behind on the other 8 (`PARITY.md`): the
> same algorithm under another compiler, not yet tuned for it. `PORTING.md` has the rules of the port and what it leaves out
> (environment switches, out-of-memory fallbacks, opt-in paths, the profile hooks).
>
> `sort_f64_v3` is the engine this crate had before the port: the C's architecture with thirteen routes of its own
> design in about 2,600 lines. It matches the C engine's speed on the scoreboard's shapes at 8.4M but NOT its
> decisions, and unlike the port it may be called from several threads at once. Not ported from C: int32, strings on
> prefix keys, the lazy view, the batch entry, the in-place sort's parallel form, measured memory, fault injection.
> Unreleased: the version is still 0.3.0.

## What is here

```rust
logos_sort::sort_f64(&mut a, threads);        // the C engine's algorithm (src/port; x86-64 with AVX2 and FMA, detected at run time)
logos_sort::sort_f64_witnessed(&mut a, threads, &[4, 10, 12]);   // the same, returning the C's route witnesses (tests)
logos_sort::sort_f64_v3(&mut a, threads);     // the independent v3 engine (engine.rs, par.rs); last_route() names its route
logos_sort::sort_f64_v2(&mut a, threads);     // the portable v2 engine; what the others run without AVX2
logos_sort::release_buffers();                // frees the pools and stops the worker threads
logos_sort::sort_i32, sort_f64_inplace, sort_i32_inplace, argsort_f64, argsort_i32,
            apply_permutation, inverse_permutation, find_outliers_f64, sort_strings      // unchanged from 0.3.0
```

## Contract

- Ascending, in place. Results do not depend on the thread count as multisets; equal values (and -0.0 / +0.0) may come
  out in any order relative to each other, and the sort is not stable.
- Infinities, subnormals and signed zeros are ordinary values and are tested. With a NaN in the array the ORDER is
  unspecified; what holds, and is tested, is that the call returns and the output is a permutation of the input's bit
  patterns (payloads included).
- Arrays of 2^32 elements or more, and machines without AVX2 + FMA, get the v2 engine.
- **`sort_f64` sorts one array at a time**, as the C engine does (its pools and context bundles are process-wide): a
  second caller waits for the first. `sort_f64_v3` runs concurrently (a second caller of its busy worker pool sorts on
  its own thread).
- Scratch: up to 8 bytes per element at one thread (the run routes take 9), about 14 at fourteen threads on the
  partition. These are what the code ASKS for; nothing here measures memory, asked or resident. Buffers are kept
  between calls until `release_buffers()`.
- An allocation failure aborts, as anywhere in Rust. A worker thread that cannot be started costs speed only (work is
  claimed from a counter and the caller takes part), but that path has no test.

## Safety story

**The port is unsafe Rust throughout, by design**: raw pointers, `static mut` globals and the C's names, so that it
can be read against the C line by line. Its safety argument is the C engine's, plus the route checker and 80 unit
tests; it has not been run under Miri or a sanitizer, and none of the C harness's 55,809 checks have been ported.

The v2 engine was safe Rust but for one scatter. **The v3 engine is not** either: the kernel is AVX2 intrinsics over raw
pointers, the routes write through raw pointers into scratch and back, and worker threads share the array through a
`Send` wrapper. What stands in for the borrow checker is the test suite's two properties on every output (order under
`<`, and the bit patterns as a multiset) over every route, plus the rule that each parallel phase hands out disjoint
work: chunks of the input by index, buckets and placement jobs by output range. Two defects of exactly this kind were
found by those tests and are recorded in `PARITY.md`. The code has not been run under Miri or a sanitizer.

## Build, test, measure

The toolchains live in WSL here (rustup in `~/.cargo`, GCC for the C engine); build products go outside the tree.

```sh
bash parity/test.sh                               # cargo test --release (85 tests)
bash parity/routes.sh 3000,1000003,8388608 1,4,14 # ROUTE equivalence against C; ROUTES_VERBOSE=1 prints the witnesses
bash parity/porttest.sh                           # the port's 80 unit tests, one at a time
bash parity/parity.sh 8388608 16 14               # speed: the scoreboard's 17 shapes, C against sort_f64, 1 and 14 threads
bash parity/parity.sh 8388608 12 14 extra         # the 16 it was not tuned on
bash parity/kernbench.sh                          # the two AVX2 kernels alone
bash parity/trace.sh 8388608 1 block              # which route took a shape, and where its time went
cargo run --release --example bench               # the old fair fight against sort_unstable and rayon
```

## History: the v2 engine

`sort_f64_v2` is the engine this crate began with: a parallel sample sort over a coarse interpolation leaf, safe Rust
but for one scatter, with `sort_unstable` as its worst case. Against `sort_unstable` at 8M on one core it won 2 of 8
shapes (int_wide 1.27x, uniform 1.08x) and lost the structured ones (quantized 0.58x, few_distinct 0.38x): the shapes
the v3 routes exist for. It stays as the portable fallback and as the reference the old tests were written against.
