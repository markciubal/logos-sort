logos-sort against the fastest open-source sorts

logos-sort reads the shape of its input before it sorts. When the data has structure — stretches already in order, a handful of distinct values, numbers on a fixed grid, sorted blocks in the wrong order — it places elements by address instead of comparing them. This page times it against Intel’s x86-simd-sort, Google’s VQSort, IPS⁴o and the C++ standard library on 33 inputs, from an empty array to 50,000,000 elements, on one thread and on 14.

Where the speed comes from

Most of the inputs have structure that real data often has: logs that arrive nearly in time order, columns with few distinct values, prices on a grid of cents, shards concatenated out of order. logos detects it from a small sample and takes a route that does less work than any comparison sort can: it counts, moves whole runs, or merges only where runs overlap. On those inputs the margin generally grows with n.

Uniformly random numbers have no structure to use. On one thread logos then runs its own vectorized quicksort, the same design as x86-simd-sort and VQSort, so those rows are a race between kernels; on many threads it splits the values into ranges across all cores and sorts each range. The uniform, heavy_tail, bimodal and int_wide inputs are that case, and among the practical ones the latencies, the coordinates and the foreign keys.

What changed in the engine this month

  • More threads for mid-sized random data. Between about 300,000 and a million elements, data with no structure used to get one thread per 100,000 elements. It now gets one per 25,000: 1.6–2.0× faster at 316,000 elements, 1.3–1.4× at 500,000 and 1.1× at a million when 14 threads are asked for. Structured inputs are untouched.
  • Popular values are counted, not moved. When a few values each hold a few percent of a column (the busiest zip codes, the best-selling product in a foreign key), the parallel sort used to fall back to a slower two-pass path. It now counts those values as it passes them and writes them out in one fill: zip_codes 1.66× and fk_zipf 1.71× at ten million elements and 14 threads. Against the other sorts at 50 million, zip_codes went from 1.75× behind IPS⁴o in the previous measurement to level with it; fk_zipf narrowed but still trails it by 1.4×.
  • A counting table that knows when to give up. On one thread, a column that looked like it had about a thousand distinct values and really had forty thousand was counted in a hash table that outgrew the cache. The table now stops at 8,192 values and hands over: zip_codes 2.0× at 100,000 elements, 1.35× at 316,000.
  • A parallel argsort. logos_argsort_f64_mt returns the permutation that sorts a column (what sorting records by a key needs) on many threads: 3–10× the one-thread argsort at 14 threads from 500,000 to 30 million keys, the identical permutation, 12 bytes of scratch per key instead of 20. It is not one of the charts below.

How long each sort takes as the input grows

One pair of charts per input: sorts that each use one thread on the left, sorts that each use 14 threads on the right. Two views of the same measurements. Per element divides each time by n, so a flat line is linear scaling and a rising one is the n log n of a comparison sort (or a cache being outgrown); its axis opens to show logos and its nearest rivals, a triangle at the top marks a point above it, and the line beneath the chart names the sorts that run off the top. Total time is how long one whole sort took, on a logarithmic axis because it runs from microseconds to tens of seconds; every sort fits, and a gap of one gridline is ten times. Hover or touch a chart in either view to read both figures for every sort at that n; the label on logos’s line gives its last point. Sizes start at 10,000, where each point is one array sorted repeatedly with the minimum kept; the full report goes down to an empty array.

Charts show

The dashed grey lines are growth guides. Each starts at logos’s time at the smallest size plotted and shows where that time would go if it grew as O(1), O(log n), O(n), O(n log n) or O(n²) from there. In the total-time view they fan out upward: O(n) climbs one gridline per tenfold n, O(n²) two and leaves the top. In the per-element view everything is divided by n, so O(n) is the flat line, O(n log n) rises gently, O(n²) shoots off the top and O(1) and O(log n) fall to the axis. A measured line that tracks a guide grows at that rate over this range; one that bends away from O(n) late is usually the data outgrowing a cache, not a change of algorithm.

The contenders

logos-sort the engine being measured: C, AVX2 kernels, its own parallel partition. In violet, its strict in-place entry, which allocates no scratch at all.
x86-simd-sort Intel’s vectorized quicksort library, built for AVX2; at 14 threads its OpenMP version. source
VQSort Google’s vectorized quicksort from Highway 1.4.0; it has no parallel form, so it appears at one thread only. source
IPS⁴o In-place Parallel Super Scalar Samplesort (KIT), a state-of-the-art comparison sort: sequential at one thread, parallel at 14. source
std::sort GCC’s introsort; at 14 threads __gnu_parallel::sort, its OpenMP mode. Every other output is checked against it.
LSD radix, timsort two reference implementations written for the benchmark (timsort in green), one thread only.

On strings the vector sorts sort numbers, not text: their string lines are their key-value sorts driven by the same 8-byte-prefix scheme logos uses, so those compare the kernels under one method. std::sort, __gnu_parallel::sort and IPS⁴o compare with strcmp.

How it was measured

  • Every output is checked against std::sort’s on the same input before its time counts. A mismatch marks the row with ✗; there are none unless one is shown.
  • Same input, best of several runs. Each size is sorted by every contender in turn from an identical copy: the fastest of 5 runs up to a million elements, of 3 up to ten million, 1 above.
  • One thread against one thread, 14 against 14. 14 is the physical core count; every parallel sort is given that many threads, IPS⁴o included.
  • Strings stop at 50M elements and the memory pass at 50M. A billion strings do not fit the machine, and per element the memory figures are flat from ten million up.
  • The machine is a laptop under WSL2, not a lab. Absolute times move by tens of percent between runs; the sorts at one size run seconds apart, so the comparisons within a chart hold, and differences under 5% count as level.
How busy the machine was, measured on one thread before the run: copying 64 MB took 3.34 ms and std::sort of a million doubles 63.5 ms. At rest it reads about 3 ms and 60 ms; well above that every absolute time is inflated, while the comparisons between sorts in one chart still hold.

Reproducing it

One command on Linux with GCC and an x86-64 CPU with AVX2. From a checkout of logos-sort, fetch the opponents beside the engine, then build and run:

cd engines
git clone --depth 1 https://github.com/intel/x86-simd-sort
git clone --depth 1 https://github.com/ips4o/ips4o
git clone --depth 1 --branch 1.4.0 https://github.com/google/highway
sudo apt install libtbb-dev                     # IPS4o links TBB
cd c && LOGOS_MAX_N=5e7 LOGOS_MAX_SEC=600 LOGOS_STR_MAX_N=5e7 LOGOS_SCALE_MEM_MAX_N=5e7 make scale-full
python ../../tools/scale_index.py ../../reports/scale-report.html ../../index.html   # this page

The run prints every time as it goes and exits non-zero if any output differs from std::sort’s. Absolute times depend on the machine; the comparisons within each chart are the result.
