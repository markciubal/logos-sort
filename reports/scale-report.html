Benchmark report

logos-sort benchmarks

logos-sort is a sorting engine that reads the shape of its input before it sorts. When the data has structure, such as stretches already in order, a handful of distinct values, numbers on a fixed grid, or sorted blocks in the wrong order, it places elements by address instead of comparing them. This report times it against the fastest open-source sorts available, on the same inputs, from an empty array to ten million elements, on one thread and on many.

At the largest size

Each bar compares logos with the fastest other sort on that input, at the largest size measured. To the right of the line logos is faster by the factor shown; to the left, the other sort is. Hover a row for both times. Differences under 5% are shown as level: that is within this machine's run-to-run noise.

Where the speed comes from

Most of the inputs below have structure that real data often has: logs that arrive nearly in time order, columns with a few distinct values, prices on a grid of cents, shards concatenated out of order. logos detects that from a small sample and takes a route that does less work than any comparison sort can: it counts, places whole runs, or merges only where runs overlap. On those inputs the margin is generally larger at ten million elements than at one million.

Uniformly random numbers have no structure to use. On one thread logos then runs its own vectorized quicksort, the same design as x86-simd-sort and VQSort, so those rows are a race between kernels; on many threads it splits the values into ranges across all cores and sorts each range. The uniform, heavy_tail and bimodal inputs are that case.

The trade is memory. logos often allocates scratch space, where std::sort and the vector quicksorts sort in place; the circles on the detailed charts show the peak heap per element for every sort.

    reading the charts in detail: the reference curves, exponents, the seam at 10k and the memory circles

    The dashed grey curves are O(n) and O(n log n) references anchored at logos's largest measured point, so a series that bends above the O(n log n) curve is growing faster than a comparison sort should. The label after each series name is its empirical exponent, the least-squares slope of log t against log n over n ≥ 100k (below that fixed costs dominate). The single-threaded panel compares sorts that each use one thread; the parallel panel compares sorts that each use the same P threads (VQSort, the LSD radix and timsort have no parallel form and appear in the first only). Every output was checked equal to std::sort's on the same data; the minimum of the repetitions is plotted. A line that stops early hit the per-sort time budget.

    Each panel holds two charts of the same measurements: time per sort, and below it nanoseconds per element, whose value axis is always linear (only its n axis follows the axis toggle). n = 0 is the cost of one call: it has no per-element value, and it cannot sit on a log axis, so the log view leaves it to the tables. The size buttons cut every chart down to the small end, because a linear n axis puts everything below a million into its first pixels. The last row of the ns-per-element table is the scaling slope read off two points: with c the cost per element, p = 1 + ln(c_hi / c_lo) / ln(n_hi / n_lo), so p = 1 is linear scaling and the percentage beside it is how much dearer one element became from 1M to the largest size. Those two rows are measured minutes apart on a machine whose speed drifts, so read that row as a sketch: make slopebench measures the same number in adjacent pairs, where the drift cancels. Sizes below 10k are timed as batches of distinct inputs sorted back to back, since one such sort is shorter than the clock can resolve and repeating one input would train the branch predictor; the parallel sorts are called with all threads there too, so what they show at small n is what such a call costs. That change of method is a SEAM, and the dashed line marks it. Three things flip there at once, all favouring the right-hand side: the working set (a batch is about 2 MB and exceeds L2, one array at n = 10k is 78 KB and does not), the branch history (every batch instance is a different input; the single array is the same input every rep), and the statistic (a batch's total divided by its count, against the minimum of several reps). So a curve may be read along either side of the line, but a step ACROSS it is partly the method. The batch ÷ single row in the ns-per-element table measures that step for this panel: the same n timed both ways, at the one size where both modes resolve. Use it to tell the two apart. Where it is well above 1 a jump at the line is the harness; the sequential contenders sit around 2-4x. Where it is near 1 and the chart still jumps, the jump is real and belongs to the data - a shape is not the same shape at 3162 as at 10000, since the number of runs, cycles or distinct values in it moves with n, and the engine's routing gates are ratios of n. Both happen in this report. The extreme values, tens to hundreds, are all __gnu_parallel::sort at P threads, and they are not a measurement fault but the point restated: a batch calls the sort 26 times back to back, so 26 parallel regions are opened and joined on 10k elements, where the single measurement opens one and keeps the best of five. Everything that panel plots LEFT of the line for a parallel contender is dominated by that per-call cost rather than by sorting, which is what "the parallel sorts are called with all threads there too" means in practice. The circle around a point is memory: the peak heap of one COLD call at that size, in bytes per element, measured in a pass of its own after all the timing (releasing the pools is what makes a call cold, and doing that between timed rows would have left the next row paying for its buffers). The value is the circle's RADIUS: the largest reading anywhere in the report is 15 px and every other scales linearly by it, so a circle means the same number in every panel; with a linear radius, twice the memory draws four times the ink, so read them as ranks rather than areas. The numbers themselves are in the tooltip (the peak heap column, bytes per element and the total it means at that n) and in each panel's third table. No circle means nothing was allocated - std::sort and the strict in-place entry draw none at any size - and sizes below 10k have none because a size there is a BATCH of distinct inputs, where a peak would be the batch's and not one sort's. Per element, not absolute: absolute bytes would simply grow with n and say nothing, and this way the small-n rows show the fixed pool costs before they amortize.

    The 17 shapes: what each one is, with demo data from its own generator

    Every shape below is drawn by the bench's own generator, seed 7, at n = 1,048,576: the data the charts sorted at that size, not a picture of it. Left, the whole array at 512 evenly spaced positions; right, 48 consecutive elements around the feature that defines the shape (in orange where there is one), and below them twelve of those values in the order the sort receives them. The line under each description counts all n elements. Strings have no numeric value, so they are plotted by rank, their position in sorted order. Shapes are defined partly in proportion (64 blocks, 32 cycles, n/100 swaps) and partly in absolute terms (noise of ±50 or ±60), so at small n the second kind is relatively noisier, one reason a curve can bend between sizes. The batches below 10k use seeds 7, 8, 9, … for their instances. Each panel's heading links back to its entry here.

    Reproducing it

    Everything here is one command on Linux with GCC and an x86-64 CPU with AVX2. From a checkout of logos-sort (github.com/markciubal/logos-sort), fetch the opponents beside it, then build and run:

    cd engines
git clone --depth 1 https://github.com/intel/x86-simd-sort
git clone --depth 1 https://github.com/ips4o/ips4o
git clone --depth 1 --branch 1.4.0 https://github.com/google/highway
sudo apt install libtbb-dev          # the IPS4o build links TBB
cd c && make scale-full              # about ten minutes; writes scale-report.html

    The run prints every time as it goes and stops with an error if any sort's output differs from std::sort's. Absolute times depend on the machine; the comparisons within each chart are the result.
