Idea
the histogram computes each element's bucket with a 7-step dependent-load binary search over 79 splitters. Build once, from the sorted sample, a 4096-cell equi-width table over [min,max] (or over the high bits of the order-preserving key for skewed data) whose cell holds the bucket when the cell lies inside one bucket, else a two-entry range to resolve with one compare. Common case: one multiply, one load.

H2Exception extraction for near-sorted data ("sort the displaced set")

Idea
near_sorted is n/100 random swaps, so ~2% of elements are displaced and 98% already form a sorted sequence. One greedy pass keeps a non-decreasing spine (append if ≥ last; on a dip, decide whether the new element or the spine's tail is the intruder by peeking one ahead, with a short pop-back cascade so the spine is sorted by construction) and compacts the intruders into an exception list. Sort the exceptions with the engine (tiny), then one galloping two-stream merge of spine + exceptions back into a[]. Every pass is sequential; the only comparison work is over the 2%. Abort budget: if exceptions exceed ~5% of n, fall back to the existing path (same shape as the momentum displacement budget). Parallel: chunk the extraction, fix chunk boundaries, band-merge as D4 already does.
Why it is new
C5 tuned the merge kernel; D4 changed the partition. Neither reduces the element count that goes through comparison. The current path (runs bail because avg run ≈100 < 256; momentum declines) ends in the coarse scatter, which is only fast here because writes happen to be near-sequential.
Prediction
near_sorted 1T 37 → 12–18 ms; 20T 22.5 → 5–8 ms (a clear win over x86-simd-sort's 24.8, today a tie). segmented / few_runs / prefix_shuffle unchanged (run-merge still catches them).
A/B
interleaved, shapes near_sorted at swap rates 0.1%, 1%, 5%, 10% to find the crossover and confirm the abort budget works.
Cost
medium. New algorithm, ~150 lines, needs its own harness shapes at several swap rates.

H4Equi-depth coarse bucketing from the sample CDF (one path for value-coarse and bits-coarse)

Idea

Why it is new

Prediction

interleaved coarse-slot variants; grade on those three rows.

medium. Risk: the table build per recursion level is a new fixed cost (B4); keep it to the top coarse level only.

H6Branchless / SIMD sorting network at the ≤64-element leaf

Idea

Replace with a bitonic network (8 AVX-512 registers hold 64 doubles; x86-simd-sort's sort_n templates already implement it) or, portably, a cmov-based network for ≤16 and a merge.
Why it is new

Prediction
uniform 1T −10 to −15%; 20T −5%; nothing on the counting paths. If H0 shows the leaf under 10% at 1T, skip.
A/B
interleaved leaf variants, uniform / heavy_tail / int_wide.
Cost
low with x86-simd-sort at hand; medium portable. Update 2026-09-10 (after H0b and make leafbench, C17): the leaf is now the largest parallel phase (40–56% of wall). On a ~100k bucket it is flash sort: equi-width classes with m = n, a scatter, and one insertion pass that repairs local disorder at a cost ∝ n·∫f² over the bucket (Devroye, L2). Changing the class count or routing to coarse did not help universally, which localises the cost in the repair pass and the per-bucket probes. Three levers, in order:
  1. Equi-depth classes gated by an ∫f² estimate. The bucket's existing 64-sample gives the estimate (sum of squared cell occupancies); flat → keep the multiply; skewed → classify by a 64-segment piecewise-linear CDF. Prediction: heavy_tail and bimodal leaf −20 to −30%, uniform ±2%.
  2. Line-granular branchless repair. Load eight doubles, one shifted SIMD compare + movemask; if the line is in order and its first element ≥ the previous line's last, skip it; else fix the line with a small network. Flash output makes the skip the common case. Prediction: leaf −10 to −15% on every shape.
  3. Drop the per-bucket probes (J2): prescan, run detection, inversion and gap samples re-derive what the histogram and the splitters already know. Prediction: leaf −10%.

Each is a day with the interleaved A/B; do 1 first because it is the one Devroye's model predicts most confidently. Lever 2 BUILT, measured mixed over three runs, kept opt-in (-DLOGOS_LINE_REPAIR: branch-free 8-element network per line, then a predictable insertion pass). Run 2: within ±5% everywhere; run 3: +35% heavy_tail, +40% bimodal, −4% uniform, all at 20T. The mechanism argument predicted a small universal gain; the data says shape-dependent and noisy. A quiet-box A/B decides it. Levers 1 and 3 remain open.

Reading across the rows. The theory is right about what to avoid (data-dependent comparison trees) and wrong about why it is expensive: the cost on this hardware is random access and dependent loads, not the comparison instruction. logos avoids comparisons by introducing an address computation that is itself a dependent-load search (K1) plus a random-access scatter (K3), and it pays for structure detection on every input (K2, K7). The optimal algorithm for unstructured keys on a CPU is a streaming one: few passes, sequential access, branchless inner loops, whether it compares (SIMD quicksort) or addresses (radix with O(1) digits). logos already is that algorithm on the lattice, counting and now block-permuted paths, which is why those rows win. The unstructured rows lose by exactly the two things the profiler put numbers on: the splitter search and the branchy leaf, together ~90% of parallel CPU. Both have avenues with written predictions (H0b, H6). Everything else in this table is bounded by the two-to-four-pass floor, which no restructuring within "produce the array" can beat, and that floor is the honest end of the thesis.

The engine guesses once from a sound sample and never narrows. The cheapest genuine narrowing is J16 (regroup on the exact counts), then equi-depth leaf classes gated by the L2 estimate; sketches belong in the query API and the streaming probe, not in the partition.

Physical properties that make neighbour checks cheap (relevant to the leaf fix-up and the piggybacked probes): a cache line is eight doubles, so comparing an element with its line-mates costs no memory traffic; the hardware prefetcher runs a neighbour-wise scan at bandwidth; one SIMD compare of a register against its one-lane shift yields "a[i] ≤ a[i+1]" for eight pairs, a second gives equality, an OR of key bytes gives the byte-skip mask; AVX-512 conflict detection finds equal values within sixteen lanes (useless as a histogram, C2, but exactly a similarity check on data already in the register). Nothing is content-addressed: caches and TLBs hash on address, so "values near x" can only be found after placing by value, which is what the partition is for.
